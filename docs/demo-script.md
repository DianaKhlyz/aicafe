# Демонстрация: полные сценарии всех возможностей

Как установить демо — [deploy/demo-install.md](../deploy/demo-install.md).
Ниже — сценарии показа каждой возможности: подготовка, шаги, что
подчеркнуть и что из этого следует для планирования.

## Подготовка (5 минут до показа)

1. **Перезапустить бэкенд** (`systemctl restart aicafe` или локально
   перезапустить `make dev-backend`). Это сбрасывает счётчики мок-заказов —
   нужно для сценария с трекером (см. ниже).
2. Открыть сайт **с телефона** (или в мобильном режиме браузера) — сайт
   mobile-first, так он выглядит как задуман.
3. Держать под рукой ноутбук со вторым окном сайта и терминалом —
   для «вау-моментов» с реальным временем.
4. В командах ниже заменить `BASE` на адрес бэкенда:
   `https://демо-домен.ru` (сервер) или `http://localhost:8000` (локально).

Демо идёт на мок-данных: меню, зоны, залы, столы — фикстуры, повторяющие
структуру реального iiko. После подключения ключа данные станут
настоящими, ни один экран не изменится.

## Сценарий 1. Витрина и меню

**Показ:** главная → «хиты» → «Смотреть меню» → поиск («том»), фильтры-чипы
(«острое», «веган»), «Исключить аллергены» (выбрать «молоко» — меню
перестроится) → карточка блюда (КБЖУ, аллергены) → «В корзину».

**Подчеркнуть:** хиты, теги, КБЖУ, аллергены и фото — всё это персонал
редактирует в привычном iiko (внешнее меню), сайт подхватывает сам.
Двойного ведения меню нет в принципе.

**На будущее:** качество витрины = качество карточек в iiko. Запланировать:
кто заполняет внешнее меню; фотогайд для персонала (уже в брифе дизайнера);
бейджи «новинка»/«хит» — какими тегами пользоваться.

## Сценарий 2. Стоп-лист в реальном времени (вау-момент №1)

**Подготовка:** открыть меню на телефоне И на ноутбуке одновременно.

**Показ:** в терминале выполнить:

```bash
curl -X POST BASE/api/webhooks/iiko -H 'Content-Type: application/json' \
  -d '[{"eventType":"StopListUpdate","eventInfo":{"items":[{"productId":"dish-raf"}]}}]'
```

«Раф лавандовый» гаснет на обоих экранах без перезагрузки, кнопка
сменяется на «Закончилось».

**Подчеркнуть:** это имитация ровно того сигнала, который пришлёт реальный
iiko, когда на кассе поставят блюдо в стоп. Гость никогда не закажет то,
чего нет. Вернуть блюдо: та же команда с `"items":[]`.

**На будущее:** API отдаёт и остатки — можно показывать «осталось 2 порции»
(создаёт срочность). Решить, нужна ли эта надпись.

## Сценарий 3. Доставка: адрес, зоны, минимальный заказ

**Показ:** корзина → «Оформить» → режим «Доставка» → телефон → в поле
адреса набрать «Тверская» → выбрать подсказку «ул Тверская, д 7» →
появляется плашка «Зона „Центр“: доставка бесплатно, минимальный заказ
800 ₽». Если сумма меньше — сайт покажет «не хватает N ₽» и не даст
оплатить. Затем набрать «Зеленоград» → «адрес вне зоны доставки».

**Подчеркнуть:** все проверки — ДО оплаты, а не звонком после. Зоны
рисуются на странице «Доставка» (открыть — карта с полигонами и
условиями) и редактируются в iiko.

**На будущее:** запланировать реальные зоны (границы, минималки, цены) —
вопрос владельцу; подсказки адресов станут боевыми после бесплатной
регистрации DaData; финальный вид карты — за дизайнером.

## Сценарий 4. Самовывоз с честным временем готовности

**Показ:** чекаут → «Самовывоз» → пункт «К ближайшему времени (~32 мин,
с учётом загрузки кухни)» либо выбор конкретного времени.

**Подчеркнуть:** 32 минуты — не константа, а расчёт: базовое время + очередь
активных заказов на кухне. Заказы из Яндекс Еды тоже попадают в iiko —
значит, и они учитываются в очереди. Гость получает честное время, кухня —
защиту от «обещали за 15 минут в час пик».

**На будущее:** формула калибруется на реальной кухне; вопрос владельцу —
базовое время готовности среднего заказа.

## Сценарий 5. Живой трекер заказа (вау-момент №2)

**Подготовка:** важно — это должен быть **первый заказ доставки после
перезапуска бэкенда** (тогда его id в «iiko» = `mock-delivery-1`).

**Показ:** оформить заказ доставки (адрес «Тверская, 7») → откроется
трекер «Принят → Готовится → В пути → Доставлен». В терминале:

```bash
curl -X POST BASE/api/webhooks/iiko -H 'Content-Type: application/json' \
  -d '[{"eventType":"DeliveryOrderUpdate","eventInfo":{"id":"mock-delivery-1","status":"cooking"}}]'
```

Шаг «Готовится» подсвечивается сам, без перезагрузки. Повторить со
статусом `on_the_way` — «В пути».

**Подчеркнуть:** в бою статусы шлёт сам iiko, когда кухня и курьер меняют
их на своей стороне. Гость не звонит «где мой заказ» — он видит.

**На будущее:** к трекеру привяжутся уведомления в Telegram (вместо SMS)
и запрос отзыва после закрытия заказа (фаза 2).

## Сценарий 6. Бронь стола по карте зала (вау-момент №3а)

**Подготовка:** страница «Бронь» на телефоне и на ноутбуке одновременно.

**Показ:** карта двух залов, стол №3 серый (занят). На телефоне выбрать
стол №1 → форма (телефон, гости — селект ограничен вместимостью стола,
время) → «Забронировать». На ноутбуке стол №1 сереет сам — второй гость
уже не выберет его.

**Подчеркнуть:** схема зала (включая расположение столов) приходит из
iiko — переставили столы в реальном зале и в iiko, сайт перерисовался.
Брони хостес из iiko прилетят на эту же карту тем же путём.

**На будущее:** длительность слота (сейчас 2 часа) — вопрос владельцу;
предзаказ блюд к брони по предоплате — фаза 2, требует согласования;
занятость по выбранному времени (а не «сейчас») включится с реальным iiko.

## Сценарий 7. Стол по QR и общая корзина компании (вау-момент №3б)

**Подготовка:** два телефона (или телефон + ноутбук). В бою на столе
будет наклейка с QR; в демо просто открыть на обоих `BASE-сайта/t/A2`.

**Показ:** оба устройства «за столом A2». На первом представиться «Аня»,
добавить сырники; на втором — «Борис», добавить раф. Корзина стола общая:
оба видят обе позиции с подписями «кто добавил», меняют количество.
«Оформить заказ стола» с любого телефона → заказ ушёл, корзина очистилась
у всех.

**Подчеркнуть:** это решает вечную проблему «соберите один заказ на всю
компанию». Та же механика позже сработает для офисных заказов доставки
(«скинь ссылку коллегам»).

**На будущее:** оплата за столом (СБП/карта), чаевые и разделение счёта
«каждый за своё» — фаза 2, после выбора банка; данные для этого уже
собираются (позиции подписаны гостями). Вызов официанта кнопкой — фаза 2.

## Сценарий 8. Личный кабинет и повтор заказа

**Показ:** «Личный кабинет» → телефон → «Получить код» → ввести **0000**
(демо-код, в бою — звонок-сброс или код в Telegram) → история заказов →
«Повторить» у любого заказа → корзина наполнилась → на главной появился
блок «Как обычно?» → в чекауте телефон уже подставлен.

**Подчеркнуть:** вход строго опционален — гостевой заказ никуда не делся.
Если блюдо из прошлого заказа сейчас в стопе, повтор честно скажет об
этом и добавит остальное.

**На будущее:** сюда же встанут бонусы iikoCard (баланс, QR для кассы,
списание при онлайн-оплате) — фаза 3; история пополнится заказами не
с сайта (iiko умеет отдавать заказы по телефону гостя).

## Сценарий 9. Инструменты персонала (если настроен Telegram)

**Показ A — уведомления:** оформить любой заказ → в рабочей группе
мгновенно: «Новый заказ с сайта: самовывоз, 640 ₽». То же с бронью.

**Показ B — бот смен** (нужен вариант установки с доменом): написать боту
в личку → меню из четырёх кнопок → «Я на смене» → бот присылает личную
одноразовую ссылку в группу → войти по ней → «Сегодня на смене» — список
с временем входа. «Уйти со смены» — бот выводит из группы. «Постоянно
на смене» — вечерняя чистка не трогает.

**Подчеркнуть:** уведомления беспокоят только тех, кто на смене. В конце
дня бот сам выселяет всех непостоянных (час — настройка, обсуждаем).

**На будущее (фаза Б, уже в коде):** после подключения iiko бот сможет
работать вообще без кнопок — сотрудник пробил смену на кассе, бот сам
прислал ссылку; закрыл смену — сам выселил. Вопросы владельцу: граница
конца смены (полночь / час закрытия / ночные смены) и удобство механики.

## Карта «что видели → что за этим стоит → что планировать»

| Показанное | Что за этим стоит | Планирование |
|---|---|---|
| Меню, фото, КБЖУ, стоп-листы | Внешнее меню iiko, вебхуки | Кто заполняет карточки; фотогайд |
| Зоны и подсказки адресов | Полигоны iiko + DaData (бесплатно) | Реальные зоны; регистрация DaData |
| ETA самовывоза | Очередь заказов iiko | Базовое время кухни |
| Трекер | Вебхуки статусов | Уведомления в TG; отзыв после заказа |
| Карта зала | Схема залов iiko + резервы | Слот брони; предзаказ по предоплате |
| Общая корзина стола | Наш SSE + заказ на стол iiko | Оплата за столом, split, чаевые (после банка) |
| ЛК и повтор | Наша БД + история iiko | Лояльность iikoCard, QR, Wallet |
| «Оплатить» (заглушка) | Интерфейс PaymentProvider | Банк → адаптер; фискализация на физической кассе (54-ФЗ, согласовать с бухгалтером) |
| Бот смен | Bot API + БД смен | Граница смены; фаза Б (синк с кассой) |
| Внешний вид | Нейтральные дизайн-токены | Макет дизайнера ляжет поверх без переделок |

## Вопросы заказчику (собрать фидбек)

- Зоны доставки: сколько, границы, минимальные суммы, цена доставки?
- Самовывоз: базовое время готовности среднего заказа? (для формулы ETA)
- Бронь: длительность слота (сейчас 2 часа)? Нужна ли предоплата
  предзаказа к брони?
- Новости/акции: вести Telegram-канал (сайт подхватит сам) или форма?
- «Счастливые часы», конструктор блюд — интересно? (фаза 2–3)
- Стиль: референсы кафе/сайтов, которые нравятся (для дизайнера).
- **Бот смен**: какая правильная граница окончания смены — полночь, час
  закрытия кафе, «через N часов после входа»? (сейчас конфиг, полночь).
  Удобен ли персоналу вход/выход через личку бота? Есть ли ночные смены?
- **Фискализация**: подтвердить с бухгалтером схему «чек на физической
  кассе при закрытии заказа» (см. open-questions.md, раздел 2).

## Что попросить у заказчика (входные данные)

1. **iiko**: apiLogin (у дилера), подтверждение модулей тарифа Pro.
2. **Банк эквайринга** — название; остальное сделаем адаптером.
3. **DaData**: регистрация бесплатного аккаунта (только почта) → ключ.
4. **VPS + домен** — либо доступы, либо мы подберём (~700–1600 ₽/мес).
5. **Telegram**: создать бота у @BotFather (5 минут) → токен; рабочая
   группа персонала → уведомления о заказах и бронях уже работают.
6. **Контакт дизайнера** — передать docs/design-brief.md.
