## 2. Согласования с заказчиком (бизнес-решения)

- **Предзаказ к брони** — делать ли; если да, то только по предоплате.
- **«Счастливые часы»** (автоскидки против списаний) — согласовать механику.
- **Конструктор блюд** — согласовать целесообразность.
- **Лимиты внешних сервисов** — DaData (10 000 запросов/день бесплатно,
  ~400–500 адресов/день) и Яндекс.Карты: для старта хватает, при росте —
  платные тарифы.

## 3. Риски — проверить на песочнице iiko сразу после получения доступа

Доступ к iiko появится ~через месяц (от 2026-07-08). Тариф Pro.
У дилера запросить: **apiLogin для iikoCloud API**, подтверждение
доступности **вебхуков** и **внешнего меню** в тарифе.

**Обновление 2026-07-08:** структура API проверена по официальной
OpenAPI-схеме iiko (детали и соответствие фич эндпоинтам —
в [iiko-api-notes.md](iiko-api-notes.md)). Большинство рисков сняты
на уровне схемы; на песочнице проверяем только поведение.

Снято проверкой схемы API:

- ✅ **Схема залов**: `available_restaurant_sections` с `returnSchema=true`
  отдаёт полную геометрию (столы с координатами/поворотом/размерами +
  декор зала). **План А подтверждён, мини-редактор не нужен** — заказчик
  редактирует зал в iiko. Бонус: `restaurant_sections_workload` даёт
  занятость по интервалу времени (слоты — из коробки).
- ✅ **Внешнее меню**: категории с картинками, аллергены, КБЖУ, веса
  порций, фото с кропами, модификаторы с ограничениями.
- ✅ **Несколько платежей на заказ**: `payments[]` с
  `processingType: External` + `update_payments`/`change_payments`.
- ✅ **Вебхуки**: настраиваются кодом через `webhooks/update_settings`;
  есть фильтр и по заказам на столах (`tableOrderFilter`).
- ✅ **История заказов по телефону**: `deliveries/by_delivery_date_and_phone`
  — «повтор заказа» без собственной истории.
- ✅ **Валидация до оплаты**: `deliveries/check_create`.

Чек-лист песочницы (поведение, не структура):

1. Закрытие заказа несколькими External-платежами по частям (split).
2. Фактические тела вебхуков (поля eventInfo) и задержки доставки.
3. Расчёт ETA: производительность выборки активных заказов
   (`deliveries/by_delivery_date_and_status`).
4. Тип оплаты «онлайн» — корректное закрытие, чтобы касса и отчётность
   сходились.
5. Лимиты запросов iikoCloud API (в схеме не описаны) — под них
   настроить кэш и частоту синка.
6. `NutritionInfoDto` — точный состав полей КБЖУ на реальном ответе.

## 4. Зафиксированные требования к смежным работам

- **Дизайнеру**: mobile-first — жёсткое требование; проектировать от экрана
  телефона, десктоп — расширение. Один дизайн-набор обслуживает три канала
  (доставка, самовывоз, QR за столом).
- **Персоналу/заказчику**: хостес ведёт брони в iiko (иначе карта зала
  врёт); контент блюд (фото, описания) редактируется во внешнем меню
  iikoWeb; стоп-листы — только в iiko.

## 5. Процесс работы (как договорились)

1. Качество и оптимизация процессов — приоритет; скорость — в последнюю
   очередь.
2. Никакого кода до принятия решения: каждый блок обсуждаем перед
   реализацией, даже если он уже описан в этих документах.
3. Если в процессе возникают вопросы — тормозим, обсуждаем, потом
   продолжаем.
4. Изменения договорённостей вносим в эти документы, чтобы они оставались
   единственным актуальным источником решений.
5. Следующий шаг после вычитки документов: согласовать открытые вопросы
   №1–2 (фреймворк, TS) → строить каркас проекта.
