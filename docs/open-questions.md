## 2. Согласования с заказчиком (бизнес-решения)

- **Предзаказ к брони** — делать ли; если да, то только по предоплате.
- **«Счастливые часы»** (автоскидки против списаний) — согласовать механику.
- **Конструктор блюд** — согласовать целесообразность.
- **Лимиты внешних сервисов** — DaData (10 000 запросов/день бесплатно,
  ~400–500 адресов/день) и Яндекс.Карты: для старта хватает, при росте —
  платные тарифы.

## 3. Риски — проверить на песочнице iiko сразу после получения доступа

Доступ к iiko появится ~через месяц (от 2026-07-08). Тариф Pro.
У дилера запросить: **apiLogin для iikoCloud API**, подтверждение
доступности **вебхуков** и **внешнего меню** в тарифе.

Чек-лист проверок (по убыванию критичности):

1. **Несколько внешних платежей на один заказ** через API — фундамент
   split-оплаты (общая корзина стола, разделение счёта). Если iiko не
   позволит — split перепроектируем (например, дробление на подзаказы).
2. **Данные для расчёта ETA самовывоза** — какие поля по активным заказам
   и кухне реально отдаёт API в нашей лицензии (нужно для формулы
   «базовое время + надбавка за очередь»).
3. **Схема залов** из `reserve/available_restaurant_sections` — есть ли
   координаты/геометрия столов для отрисовки интерактивной карты зала.
4. **Внешнее меню** (`api/2/menu`) — полнота полей: витринные названия,
   описания, фото, аллергены, теги, КБЖУ.
5. **Вебхуки** `StopListUpdate`, `DeliveryOrderUpdate`, `ReserveUpdate` —
   доставка, формат, задержки.
6. **Привязка столов к QR-ссылкам** — формат кодов столов для режима
   `/t/{tableCode}`.
7. **Тип оплаты «онлайн»** — корректное закрытие заказа, чтобы касса и
   отчётность сходились.
8. **Лимиты запросов iikoCloud API** — под них настроить кэш и частоту
   синка.

## 4. Зафиксированные требования к смежным работам

- **Дизайнеру**: mobile-first — жёсткое требование; проектировать от экрана
  телефона, десктоп — расширение. Один дизайн-набор обслуживает три канала
  (доставка, самовывоз, QR за столом).
- **Персоналу/заказчику**: хостес ведёт брони в iiko (иначе карта зала
  врёт); контент блюд (фото, описания) редактируется во внешнем меню
  iikoWeb; стоп-листы — только в iiko.

## 5. Процесс работы (как договорились)

1. Качество и оптимизация процессов — приоритет; скорость — в последнюю
   очередь.
2. Никакого кода до принятия решения: каждый блок обсуждаем перед
   реализацией, даже если он уже описан в этих документах.
3. Если в процессе возникают вопросы — тормозим, обсуждаем, потом
   продолжаем.
4. Изменения договорённостей вносим в эти документы, чтобы они оставались
   единственным актуальным источником решений.
5. Следующий шаг после вычитки документов: согласовать открытые вопросы
   №1–2 (фреймворк, TS) → строить каркас проекта.
